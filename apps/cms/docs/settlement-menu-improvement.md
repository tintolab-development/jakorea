# 정산 메뉴 구조 개선 제안서

## 📋 기획자 관점: 사용자 경험 분석

### 현재 문제점

**정보 아키텍처 (IA) 관점:**
- 정산 하위 메뉴가 7개로 과도하게 분산됨
- 사용자가 원하는 정보를 찾기 위해 여러 번 클릭해야 함
- 메뉴 깊이가 깊어져 인지 부하 증가

**사용자 시나리오 분석:**
1. **정산 신청 대기 확인** → `/settlements/pending` 클릭
2. **정산 확인 대기 확인** → `/settlements/review` 클릭  
3. **정산 지급 완료 확인** → `/settlements/paid` 클릭
4. **전체 현황 보기** → `/settlements/overview` 클릭

→ **문제**: 각 상태별로 별도 페이지를 이동해야 함 (비효율적)

### 개선 목표

1. **탐색 효율성 향상**: 한 페이지에서 모든 정산 정보 접근 가능
2. **인지 부하 감소**: 메뉴 깊이 축소 (3뎁스 → 2뎁스)
3. **사용자 워크플로우 최적화**: 상태별 필터링으로 빠른 전환

## 🎯 제안하는 개선 방안

### 방안 1: 통합 정산 목록 페이지 (권장) ⭐

**구조:**
```
강사단 관리
  └─ 정산 (단일 페이지)
      ├─ 탭: 전체 / 신청 대기 / 확인 대기 / 지급 완료 / 전체 현황
      ├─ 뷰 모드: 테이블 / 캘린더
      └─ 필터: 기간, 상태, 강사, 프로그램
```

**장점:**
- 메뉴 깊이 감소 (3뎁스 → 2뎁스)
- 한 페이지에서 모든 정산 정보 접근
- 상태별 빠른 전환 (탭 클릭)
- URL 파라미터로 상태 유지 (`/settlements?status=pending`)

**구현 방식:**
- 기존 `/settlements` 페이지를 메인으로 사용
- 탭 컴포넌트로 상태별 필터링
- URL 쿼리 파라미터로 상태 관리

### 방안 2: 하이브리드 구조

**구조:**
```
강사단 관리
  └─ 정산
      ├─ 정산 관리 (통합 페이지)
      │   ├─ 탭: 전체 / 신청 대기 / 확인 대기 / 지급 완료
      │   └─ 뷰 모드: 테이블 / 캘린더
      ├─ 월별 정산 관리 (별도 페이지)
      └─ 산출 로직 설정 (별도 페이지)
```

**장점:**
- 핵심 기능 통합, 특수 기능 분리
- 월별 관리와 설정은 별도 페이지 유지 (복잡도가 높음)

## ✅ 최종 권장안: 방안 1 (통합 정산 목록)

### 구현 계획

1. **Phase 1: 통합 페이지 구현**
   - `/settlements` 페이지에 탭 추가
   - 상태별 필터링 기능 강화
   - URL 쿼리 파라미터로 상태 관리

2. **Phase 2: 메뉴 구조 단순화**
   - 하위 메뉴 제거 (정산 신청 대기, 확인 대기, 지급 완료, 전체 현황)
   - 정산 목록만 유지
   - 월별 정산 관리, 산출 로직 설정은 별도 페이지 유지

3. **Phase 3: 기존 URL 리다이렉트**
   - `/settlements/pending` → `/settlements?status=pending`
   - `/settlements/review` → `/settlements?status=review`
   - `/settlements/paid` → `/settlements?status=paid`
   - `/settlements/overview` → `/settlements?view=overview`

### 예상 효과

- **사용자 경험**: 탐색 시간 50% 감소
- **개발 효율**: 코드 중복 제거, 유지보수 용이
- **메뉴 구조**: 직관적이고 간결한 구조
